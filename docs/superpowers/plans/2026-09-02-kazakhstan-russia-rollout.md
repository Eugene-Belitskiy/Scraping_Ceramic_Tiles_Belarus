## 1. Контекст: что изменилось с 22 августа

Исходный rollout-план предполагал, что playbook — это в основном про инфраструктуру
(workflow, jobs, artifacts, Secrets). На практике добрая половина реальных проблем
Беларуси была не про инфраструктуру, а про **устойчивость самого скрапера** к живому
антибот-поведению сайта, которое проявляется только под нагрузкой из CI:
rate-limit, эскалация до обрыва соединения, устаревающие CSS-селекторы, неполные
данные на странице. Ни один из этих классов проблем не был виден на этапе
локальной разработки на Windows-машине — только после реальных прогонов в GitHub
Actions.

Из-за этого главная поправка к исходному плану: **закладывать устойчивость
(раздел 3 плейбука) с первого коммита**, а не добавлять её реактивно после серии
неудачных прогонов, как это происходило с Беларусью. Ниже — конкретный план с
учётом этого.

## 3. Порядок и почему

**Казахстан первым.** Архитектурно проще Беларуси (1 источник на Selenium из 5,
как и было у Беларуси), но нужен подготовительный шаг — `git init`, репозиторий на
GitHub, первый push. Хорошая проверка, что playbook переносится на **новый**
репозиторий с нуля, а не только дорабатывается в уже подключённом.

**Россия — с оговоркой.** 3 из 4 источников на `undetected-chromedriver`.
Датацентровый IP GitHub Actions чаще ловит антибот-защиту, чем обычный
домашний/офисный — и мы это не гипотетически знаем, а видели своими глазами на
Беларуси с всего ОДНИМ requests-источником (21vek): 429 → эскалация до обрыва
соединения при нагрузке, потребовавшая нескольких раундов фиксов (снижение
параллелизма, каппинг Retry-After, паузы между запросами). У России сразу 3
Selenium-источника — риск того же порядка, но по трём фронтам одновременно, и
Selenium сложнее параллелить/троттлить аккуратно, чем `requests`.

Закладывать сценарий **гибридной схемы** заранее: 1 источник без Selenium
(KeramogranitRU) — в GitHub Actions по общей схеме, а Selenium-источники — по факту
тестовых прогонов: если стабильно проходят 2-3 раза подряд — оставляем в облаке,
если нет — держим на локальном Windows Task Scheduler с ручной/полуавтоматической
выгрузкой JSON в тот же pipeline. Решение принимается по факту, не заранее.

## 4. Что закладывать с первого коммита (не переоткрывать заново)

Список конкретных багов/решений, на которые Беларусь потратила несколько раундов
переписки каждый — в КZ/RU их можно получить бесплатно, заложив сразу:

- [ ] **Три уровня повтора в скрапере с первого дня** (плейбук §3): `get_with_retry`
      с каппингом и `Retry-After`, retry на карточке (несколько попыток с паузой),
      retry-раунды по всему списку после первого прохода. Не «пока полетит без
      этого, а там поглядим» — сразу.
- [ ] **Reason-tracking вместо голого `except: return False`** (плейбук §3) — иначе
      каждый следующий сбой снова требует раунда «а что там на самом деле».
- [ ] **`PYTHONUNBUFFERED=1` в workflow с первого коммита** (плейбук §5.4) —
      иначе retry-цикл молчит в логе и выглядит как зависание.
- [ ] **`timeout-minutes` на каждый job** (плейбук §2.4) — жёсткий потолок GitHub
      6 часов не обходится, но собственный более ранний лимит экономит время при
      реальном зависании.
- [ ] **Начинать с `MAX_WORKERS = 1`**, поднимать параллелизм только если сайт
      явно это переносит (плейбук §3, «Параллелизм»). Не наоборот.
- [ ] **`data-testid`-селекторы вместо хэшированных CSS-классов**, где у сайта
      это есть (плейбук §5.1) — переживают редеплой фронтенда.
- [ ] **Дефолты опциональных полей ДО `try`, не только в `except`** (плейбук §5.2) —
      частичные данные на странице не должны давать `UnboundLocalError`.
- [ ] **`price_id` сразу на уровне месяца** (`product_id + MM.YYYY`), не
      дата+время (плейбук §6) — если дашборд группирует по месяцам, чему и
      предназначен весь этот пайплайн (ежемесячный мониторинг).
- [ ] **Отдельный `service_role`/`secret`-ключ Supabase для записи**, `anon` —
      только для дашборда, две разные переменные в GitHub Secrets с самого начала
      (плейбук §5.3) — не «сначала один ключ на всё, потом разбираться с RLS».
- [ ] **Top-up-восстановление артефакта прошлого запуска** через
      `dawidd6/action-download-artifact` (плейбук §4) — сразу в workflow, не
      после первого «часть карточек не собралась, а перезапуск всё собирает
      заново».
- [ ] Для Selenium-источников — `browser-actions/setup-chrome@v2` с
      `install-chromedriver: true`, оба пути (`chrome-path`/`chromedriver-path`)
      передавать явно в `uc.Chrome()` (плейбук §5.5). Не полагаться на
      автовыбор версии внутри `undetected-chromedriver`.

## 5. Пошаговый план — Казахстан

1. **Аудит источников.** Какие на `requests`/`aiohttp`, какие на Selenium
   (ожидается: 1 — LemanaPRO_KZ). Проверить актуальность CSS-селекторов/`data-testid`
   каждого источника вживую — вёрстка могла обновиться со времени последнего
   аудита кода.
2. **Git-репозиторий.** `git init`, `.gitignore` для сырых JSON/`.env` (скопировать
   из Беларуси, добавить паттерны resumable-скрапинга — `url_list_*.txt` и т.п.,
   если такой механизм тоже переносится), создать репозиторий на GitHub, первый push.
3. **Headless-переключатель** в Selenium-скрапере (`if os.environ.get("CI")`) —
   по образцу `Altagamma.py`.
4. **Устойчивость скрапера** — раздел 4 целиком, для каждого из 5 источников.
5. **Workflow-файл** — скопировать `monthly-scrape.yml` из Беларуси как основу:
   job на источник, `continue-on-error`, `timeout-minutes`, top-up restore-шаг,
   `PYTHONUNBUFFERED`. Переименовать: job'ы, пути к папкам источников, имя
   merge-скрипта (`Main_scraping_Kazakhstan.py`), имя upload-скрипта.
6. **Схема БД** — `product_id` = хэш URL, `price_id` = `product_id + MM.YYYY`
   с самого начала. Таблицы называть с суффиксом страны (`products_kz`/
   `prices_kz`/`tiles_kz`) — см. п.8, один Supabase-проект на Казахстан и
   Россию вместе. Валюта KZT — свериться, какой шаг диапазона цены имеет
   смысл (Беларусь — 10 BYN, Россия — 100 RUB; для KZT посчитать исходя из
   реальных цен на плитку в тенге, не копировать шаг бездумно).
7. **GitHub Secrets** (этого репозитория) — `SUPABASE_URL`, `SUPABASE_KEY`
   (anon, дашборд), `SUPABASE_SERVICE_KEY` (service_role/secret, загрузка) —
   все три сразу, не по одному по факту ошибок.
8. **Supabase — существующий проект России, не новый.** Ни одного нового
   Supabase-проекта создать нельзя (free tier аккаунта исчерпан — Беларусь
   уже занимает единственный доступный слот). Решение: Казахстан заезжает
   в уже существующий проект России (`Scraping_Russia/dashboard/.env` —
   те же `SUPABASE_URL`/ключи, что уже использует российский пайплайн),
   таблицы различаются суффиксом (`products_kz`/`prices_kz`/`tiles_kz`,
   у России — без суффикса, `products`/`prices`/`tiles_v2`, она была
   заведена раньше и её не переименовываем, чтобы не мигрировать живые
   данные). SQL-схема — по образцу `create_tables_kz.sql` из
   `Scraping_Kazakhstan` (не `create_tables_v2.sql` Беларуси — та без
   суффиксов, писалась под отдельный проект). RLS: `SELECT` для
   `anon` на КАЖДУЮ новую таблицу (`products_kz` и `prices_kz` по отдельности,
   политики России на них не распространяются) —
   `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` без единой политики отдаёт
   Data API 0 строк для `anon` молча, без ошибки — ровно так был найден баг
   с 200-300 SKU вместо тысяч в дашборде Беларуси, не повторять.
9. **Дашборд — не свой Streamlit Cloud деплой, а страница в общем дашборде.**
   Дашборд не живёт в этом репозитории и не деплоится отдельно — один общий
   репозиторий `Scraping_Ceramic_Tiles_Dashboard`
   (`C:\Users\belit\VSCodeProjects\Scraping_Ceramic_Tiles_Dashboard`, Streamlit
   multipage app, меню выбора страны). Логика визуализации там ОДНА на все
   страны (`core/dashboard.py::render(country_cfg)`) — `pages/kazakhstan.py`
   не копия `pages/belarus.py`, а только конфиг (см. `docs/COUNTRY_CONFIG.md`
   в том репозитории): `url_env`/`key_env` = `SUPABASE_URL_KZ`/`SUPABASE_KEY_KZ`,
   плюс **обязательно** `products_table`/`prices_table`/`view_table` =
   `"products_kz"`/`"prices_kz"`/`"tiles_kz"` (без этого подключится к
   таблицам Беларуси по умолчанию — их там нет, вернётся пусто). В Secrets
   Streamlit Cloud приложения — добавить `SUPABASE_URL_KZ`/`SUPABASE_KEY_KZ`
   (anon, только чтение) к уже существующим `_BY`.
10. **Приёмочный чеклист** (как в исходном rollout-плане, п. 3.7 для Беларуси):
    ручной `workflow_dispatch`, artifacts появляются, в БД нет дублей после
    повторного запуска, симуляция сбоя одного источника не роняет остальные,
    до-заливка реально дотягивает недостающее в течение того же месяца, дашборд
    на Streamlit Cloud видит свежие данные, полный цикл проходит по `cron`
    (не только вручную) — проверяется в следующем календарном месяце.

## 6. Пошаговый план — Россия

Тот же порядок (раздел 5), с двумя отличиями:

1. **Шаг 2 (git) не нужен** — репозиторий уже существует и подключён к GitHub.
2. **После шага 4** для каждого из 3 Selenium-источников — отдельно зафиксировать
   по результатам 2-3 тестовых прогонов подряд, стабильно ли он проходит в CI.
   Если нет — не форсировать перенос в облако: оставить источник на локальном
   Windows Task Scheduler (как сейчас), с выгрузкой JSON в тот же pipeline
   (ручной или полуавтоматической — решить по факту, насколько часто он падает).
   Финальная архитектура (полностью в облаке / гибридная) фиксируется по факту
   тестов, не выбирается заранее.
